This document records the security decisions for the local/offline Entry Control System application across authentication, roles, permissions, audit logging, backup/recovery and licensing.

## Current Decision Summary

- The default installation is local-only. The app should bind to the same machine by default, not expose the UI/API to the local network.
- LAN/multi-device use is out of scope for the default product. It can be designed later as a custom deployment for specific customers.
- The app must have login, roles, permissions, and audit logs. A sensitive gym/payment/access-control app is not acceptable without them.
- A vendor maintenance role may exist for software-owner support and recovery, but it must be disabled by default and must not be an always-active backdoor.
- The gym owner can manage gym users and roles, but cannot delete, weaken, or silently modify an active vendor maintenance account/session.
- Licensing is finite-term and offline-first, with both fully offline request/response activation and optional outbound online management.
- Online suspension/revocation becomes effective on the next authenticated check-in or the end of the last signed offline allowance; an immediate command to a disconnected machine is not claimed.
- If the license expires and grace is exhausted, the app locks most functionality.
- Emergency backup and license renewal must remain available when locked.
- Confirmed License tamper is quarantined and fail-closed but never deletes customer data; ambiguous storage, clock or hardware failure enters a recoverable restricted state.
- Restore is more dangerous than backup and must remain vendor-maintenance-only for now.

## Network Exposure

Default mode:

```text
Local-only
```

The app should be accessible from the installed PC only, for example:

```text
http://localhost:<port>
```

Default installations should not expose the app as:

```text
http://192.168.x.x:<port>
```

Rationale:

- The current target environment is offline and single-machine.
- Reducing network exposure lowers the risk from Wi-Fi users, other PCs, malware on the LAN, and accidental open access.
- LAN mode requires extra hardening, deployment controls, and support burden.

Future LAN mode:

- Design as a separate deployment profile.
- Require explicit enablement.
- Require strong admin password policy.
- Show a security warning during setup.
- Bind only to the intended private interface.
- Document firewall rules and trusted device assumptions.

The system should use fixed base roles with explicit permissions. Role names alone are not enough; authorization checks should be permission-based.

## Vendor Maintenance Account

`VENDOR_OWNER` represents software-owner maintenance access, not a normal gym account and not a permanent hidden access path.

Rules:

- Must be disabled by default on normal customer installations.
- Must not be created by public first-run setup.
- Must not use a hardcoded universal password or shared secret across installations.
- Must be activated only through an explicit maintenance workflow, such as a local maintenance script, owner-approved in-app maintenance window, or signed time-limited maintenance code.
- Should be time-limited. A maintenance account/session should automatically expire after the approved window.
- Must not be managed like an ordinary gym user.
- Must not be deletable by `GYM_OWNER` or `ADMIN`.
- Must not be demotable by `GYM_OWNER` or `ADMIN`.
- Should be allowed to sign in during license lock, but only for License, support and Emergency Backup screens. Restore stays blocked until the License incident is recovered and the separate Restore-maintenance workflow is entered.
- Should not be used for routine gym operations such as payments or member management unless explicitly needed for support.
- All vendor-owner actions must be audited.
- The UI should make active maintenance mode visible to the customer.

Current implementation:

- `GYM_OWNER` can activate `vendor-maintenance` from Settings > Admin users with a strong temporary password, reason, and 15-240 minute window.
- The protected `VENDOR_OWNER` account is created on demand, is not assignable through ordinary admin-user management, and old vendor sessions are revoked on every activation.
- Login and `/auth/me` enforce the expiry window and automatically deactivate expired vendor access.
- `GYM_OWNER` or the active `VENDOR_OWNER` can deactivate the maintenance window; activation, deactivation, expiry, login, and failed-login paths are audited.

Implementation options:

- Create disabled during installation, or create on demand through a protected maintenance activation flow.
- Store with a protected role flag and enforce server-side restrictions.
- Avoid hardcoded universal passwords.
- Require a strong password and support a secure recovery/reset procedure.
- Prefer signed offline maintenance codes for stronger customer-specific support. The app can generate a request code, the software owner signs a time-limited response code offline, and the app verifies it with a bundled public key.

## Authentication Policy

Recommended implementation:

- Server-side session auth.
- HTTP-only cookies.
- Do not store auth tokens in `localStorage`.
- Password hashing with `argon2id` preferred; `bcrypt` acceptable if argon2 is not practical.
- First-run setup creates at least one `GYM_OWNER`.
- Vendor maintenance activation must be protected, disabled by default, audited, and not equivalent to a normal user signup.
- Inactive users cannot sign in.
- Password reset must be explicit and audited.

Session policy:

- Default session duration: 8 to 12 hours.
- Logout should invalidate the session.
- Password change should invalidate other sessions for that user.
- License lock should restrict post-login permissions, not bypass authentication.

Password policy:

- Minimum 10 characters for owner/admin/vendor roles.
- Minimum 8 characters for lower roles.
- Block common weak passwords.
- Require current password for password change.
- Store only password hashes, never plaintext.

Failed login policy:

- Record every failed login attempt.
- Show generic login errors; do not reveal whether username exists.
- Lock or throttle after repeated failures.
- Suggested default: after 5 failed attempts within 15 minutes, delay or temporary lock for 15 minutes.
- `FailedLoginAttempt` already exists in schema and should be wired into auth.

## License Policy

The authoritative v1 contract is [Licensing Security and Operations Design](../licensing/design/LICENSING_DESIGN.md). Its mandatory security properties are summarized here:

- All Entitlements are finite. Daily, weekly, monthly, annual and exact custom intervals are supported; permanent/lifetime values are rejected.
- `OFFLINE_BOUND` uses a signed request/response file and needs no Internet during its valid interval.
- `HYBRID_LEASED` uses outbound authenticated check-in, short signed Leases and an explicit offline allowance.
- V1 uses deterministic CBOR/`COSE_Sign1` with `ES256`. The customer artifact contains public verification keys only.
- `LIC-6.2-001` freezes the exact [protocol v1 registry, CDDL and negative corpus](../../licensing/protocol/v1/README.md): mandatory tag 18/embedded payload/empty external AAD, exact headers/media/signer purposes, byte caps, 23 License Features, zero-alias Vendor Lease endpoints, 224 malformed descriptors and all 90 ordered cross-type rejects. It contains no key, signed token, parser or runtime authorization.
- Vendor root, Offline Entitlement, Online Lease, Offline Control, Recovery and Authenticode keys have separate purposes and custody.
- A per-installation P-256 signing key is non-exportable and TPM-backed where possible. A supported machine without usable TPM uses the lower-assurance, purpose-separated non-exportable Software-KSP wrapping-key design; standalone DPAPI-NG scopes are rejected and the signing key is never reused for wrapping.
- Binding uses the installation public-key hash, not MAC/disk/CPU inventory that would break after ordinary hardware maintenance.
- Authoritative Entitlement, revision high-water marks, clock anchor and tamper latch live under protected ProgramData, outside PostgreSQL and outside Backup/Restore.
- The existing Prisma `License` model is not authoritative and cannot admit operation.
- A separately identified .NET License Guardian exclusively owns machine identity, Secure State, official loopback proxy and program integrity. The App Host/Node run under a different SID with no direct State/key access and independently gate startup, HTTP, jobs, WebSocket and physical commands; Client is UI only.
- A locked installation keeps a verified restricted service available for Login, safe License operations, minimal redacted diagnostics, Vendor recovery and a narrow authenticated Emergency Backup facade.
- Reports/exports, business writes, manual attendance, K40 ingestion/polling/commands, enrollment, Door actuation, business jobs/WebSocket and Settings mutation are blocked before parsing or side effects.
- Invalid candidate imports are staged and rejected without replacing a currently valid License.
- Confirmed authoritative tamper is quarantined and latched. Missing/corrupt storage, TPM reset, antivirus/disk trouble and suspicious clock are recoverable failures rather than automatic accusations.
- Customer data and diagnostic evidence are never deleted as a tamper penalty. Only a one-time device/incident-bound Vendor Recovery token may clear confirmed tamper.
- License events are written to an external tamper-evident journal and a redacted database Audit projection.

No software-only design can promise absolute resistance to a local Administrator/kernel attacker, immediate revocation of a disconnected machine, or perfect detection of a complete offline snapshot/time rollback without an external or persistent TPM anchor. These are explicit security limits, not hidden implementation details.

## Audit Log

Audit logging is mandatory and should ship with auth/roles, not after.

`AuditLog` exists in schema and now has a protected read-only service, route, filter/options/detail APIs, and Settings viewer. Audit writers are present for several sensitive flows but are not yet complete across every action listed below.

Record:

- actor user id
- actor role
- action
- target type
- target id
- success/failure
- timestamp
- request IP or local client metadata
- session id or request id if available
- before/after summary for sensitive changes
- reason/metadata

Audit log visibility:

- `VENDOR_OWNER`: allowed
- `GYM_OWNER`: allowed
- All other roles: denied by default

Audit these actions:

- Login success
- Login failure
- Logout
- Password change/reset
- User created/updated/deactivated
- Role/permission changed
- Member created/updated/archived/deleted
- Membership created/cancelled/renewed
- Payment recorded/reversed
- Expense created/reversed
- Payroll payment recorded
- Manual attendance created
- Attendance justification changed
- Device created/updated/deleted
- K40 diagnostics/test/user sync/enrollment/clear logs
- Door unlock
- Sound/settings changes
- Backup created
- Restore attempted/completed/failed
- License imported/renewed/expired/locked

Audit log must be append-only at the application level. Do not build normal UI deletion for audit logs.

## Backup And Restore Security

The current backup implementation has a protected UI/API backed by the verified command workflow.

Security decisions:

- Backup creation is available to `GYM_OWNER` and `ADMIN` through `BACKUP_CREATE`.
- Restore remains vendor-maintenance-only for now.
- Emergency backup stays available during license lock.
- Backup files must not be stored in Git.
- External copies should be encrypted if they leave the gym.
- Backup UI remains permission-protected; the future License-lock path is the narrower Emergency Backup facade defined by the Licensing design, not the full Backup router.

## Open Implementation Notes

- `AdminRole` now contains the planned base roles, but authorization must still be permission-based. Legacy values remain for compatibility until the auth implementation can safely migrate old admin users.
- Use permission checks in backend routes; frontend hiding is not security.
- Existing business routes are protected server-side by permission middleware. In `FULL`, legacy push/iClock ingestion remains outside app-user authentication for compatibility. In `ATTENDANCE` v1, no public Push or iClock ingestion route is mounted; the only official ingestion path is internal polling from one enabled supported K40, gated by `DEVICES`, with Device Core physically separated from Diagnostics, Door and Push modules.
- `ATTENDANCE_POLICY=TIME_CLOCK` is not an access-control command: once the strict Staff identity boundary admits a punch, it is recorded even outside/no shift. Strict events expose `attendanceRecorded` separately from the deterministic `doorAllowed=false`/`doorOpened=false`; the compatibility `authorized` field on newly recorded strict events means accepted attendance, never permission to actuate a relay.
- Do not consider the app fully secured until complete action-level permission UI gating is implemented and sensitive workflows are audited end to end.
- Local-only binding should be part of deployment/startup defaults.
- Existing backup scripts are safe to keep outside UI until auth is ready.
- Production restore from UI should not be added until a more complete recovery workflow is designed.
