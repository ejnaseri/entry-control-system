## 1. Product decision

The selected v1 direction is a purpose-specific, machine-wide, non-exportable
wrapping key in the **Microsoft Software Key Storage Provider**. It replaces the
rejected standalone DPAPI-NG options tested through EV0117.

The following are binding:

- do not create a dedicated local user or manage a service-account password;
- do not use `LOCAL=user`, an exact service-SID DPAPI-NG descriptor or
  `LOCAL=machine` as the production state-protection boundary;
- never reuse the ECDSA installation signing key for encryption, decryption,
  wrapping or key agreement;
- never give App/Node, Database, an interactive user or a persistent Installer
  identity access to the wrapping private key;
- keep `SOFTWARE_BOUND` visibly lower assurance than TPM-backed protection and
  retain the documented full-disk/VM-clone limitation.

This decision selects a direction, not a finished adapter. LIC008 and
`LIC-OPEN-003` remain open until the harness, supported-Windows matrix,
reboot/repair lifecycle and independent security review pass.

## 2. Candidate cryptographic profile

The first implementation candidate, which must be proven before production use,
is:

| Purpose | Candidate |
| --- | --- |
| Provider | Exact `Microsoft Software Key Storage Provider` |
| Persistent wrapping key | RSA 3072-bit, machine-wide, non-exportable, encryption/decryption purpose only |
| Key-encryption operation | RSA-OAEP with SHA-256 through CNG `NCryptEncrypt` / `NCryptDecrypt`; PKCS#1 v1.5 and OAEP-SHA1 are forbidden |
| Per-envelope data key | Fresh random 256-bit key generated by the OS CSPRNG |
| State encryption | AES-256-GCM with a fresh 96-bit nonce and 128-bit authentication tag |
| Identity | SHA-256 of canonical RSA SubjectPublicKeyInfo plus the exact provider/key name in the protected ownership record |
| Private-key export policy | Export-policy DWORD `0`; every private/plaintext/archive export attempt must fail |

RSA protects only the small random AES data key. It must never encrypt License
State directly. Every new authoritative envelope uses a new AES key and nonce;
plaintext state and data-key buffers are zeroed as soon as the authenticated
transaction no longer needs them.

The final envelope schema and byte encoding belong to `LIC-6.5-002` and must be
frozen with deterministic parser vectors before production persistence. At
minimum its authenticated fields bind the format/domain version, installation,
product, Edition, state generation, wrapping-key identity, nonce, wrapped data
key, ciphertext and tag. Encryption alone is not rollback protection; the
separate journal, revision high-water and TPM/software anchor rules remain.

## 3. Key creation and ACL boundary

The signed one-shot `EntryControlSystem.Setup` service under `LocalSystem` is the
only planned creator. Creation follows the same fail-closed intent/ownership
pattern learned by the LIC008 experiments:

1. validate the signed, Edition/build-bound fixed plan and prove the helper token
   is `LocalSystem`;
2. record a no-overwrite creation intent before calling CNG;
3. create a new machine key with a collision-resistant product-owned name;
4. set length, usage and export policy before finalization;
5. apply a protected DACL containing only `SYSTEM` and the exact
   `NT SERVICE\EntryControlSystem.License` allow principals required for use;
6. finalize, reopen, read back provider/algorithm/length/usage/export/DACL and
   public identity, then run a random wrap/unwrap self-test;
7. publish the protected ownership record only after every check passes;
8. remove the temporary Setup service on both success and failure.

No broad Administrators, Users, LocalService, NetworkService, App, Database or
interactive-user allow ACE is acceptable. Windows local Administrators can take
ownership, which remains an explicit threat-model limit rather than a false
claim of protection from a fully privileged hostile administrator.

The production Guardian may reopen and decrypt with this key. App/Node and its
actual child must fail to open/use it. Error codes are not globally relabelled:
the narrow EV0107/CHG0052 `PASS_KEY_NOT_DISCLOSED` classification is usable only
when the exact provider, key identity, protected DACL, Guardian positive control
and App/child contrast all pass.

All applicable CNG calls use `NCRYPT_SILENT_FLAG`; an unexpected provider UI is
a failure. `NCryptEncrypt`/`NCryptDecrypt` work must run only after the Windows
service has completed its start callback and entered its bounded worker path;
Microsoft explicitly warns that calling `NCryptEncrypt` from `StartService` can
deadlock the service.

## 4. Lifecycle contract

| Event | Required behavior |
| --- | --- |
| Fresh install | Create exactly once through the signed Setup helper; fail and retain evidence on collision or partial creation. |
| Guardian restart/reboot | Reopen the same key, verify all properties/public identity and decrypt an existing envelope before operational admission. |
| Repair | Reconcile intent/ownership/state first. Preserve and verify a valid key; never silently replace it. |
| Upgrade | Preserve key name/material/ACL and state identity. Any cryptographic-format migration is explicit, crash-safe and rollback-tested. |
| Key missing with retained state | Enter `RECOVERY_REQUIRED`; do not create a replacement and misclassify old state as corrupt or new. |
| Key metadata/ACL/public identity mismatch | Fail closed into the documented restricted/tamper classification; do not weaken ACLs automatically. |
| Default uninstall | Preserve License State and wrapping key with the existing retained-data policy so reinstall/repair can reconcile them. |
| Explicit verified purge | Delete only through a separately authorized, exact ownership-bound flow after the product's data/license-release policy is complete; never delete by name alone. |
| Copy/clone | A copied state without the original key must fail. Full-machine/software-key copying remains lower assurance and must not be marketed as impossible. |

Repair, Upgrade and Uninstall must not call `NCryptCreatePersistedKey` merely
because `NCryptOpenKey` failed. Provider outage, ACL refusal, missing key and
wrong identity are distinct evidence and recovery cases.

## 5. First bounded harness

continuing or editing any consumed0.4.x–0.8.x package. Its controller rejects a
non-fresh root or service set and must not touch retained ComparisonV1,

The harness must prove, in order:

1. exact platform/matrix inventory and a fresh service/key namespace;
2. Setup-only RSA-3072 creation with export policy zero and exact protected DACL;
3. Guardian reopen, public-identity comparison and OAEP-SHA256 wrap/unwrap of an
   independent random 32-byte key;
4. private/plaintext/archive export refusal;
5. App, actual App child and ordinary interactive user cannot open/use the key;
6. Guardian fresh-process reopen and persisted-envelope decrypt;
7. wrong-key, modified wrapped key, nonce, AAD, ciphertext and tag rejection;

   of only fresh harness resources after ownership verification.

selection requires every applicable `WIN-V1-*` row in

independent physical computers.
